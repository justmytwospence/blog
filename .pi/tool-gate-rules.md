# Blog production approval

Production changes through CLI commands, scripts, HTTP requests, MCP tools or Git require explicit approval in the current user turn, immediately before each operation. This includes production deployment, pushing any ref that triggers production, promoting, aliasing, rollback, production environment/domain/project writes, and merging to the production branch. Approved implementation plans and earlier approvals are context, never blanket permission.

Routine preview pushes through `npm run preview:push` are authorized without another ask after local checks. The script validates this repo's exact origin and current nonproduction branch, uses an explicit single-branch refspec, and rejects arguments and force pushes. Ask for direct Git pushes and PR merges: implicit refs and configured destinations cannot be inferred safely. Ask for Vercel MCP calls and Vercel env/project/domains/api command families, including reads. Never route an operation through another tool to bypass an approval requirement.

Use Git-triggered deployments: dev owns dev.spencerboucher.com, optional feature domains are <branch>.dev.spencerboucher.com, and main remains production. Wait for the exact SHA's push CI / verify and Ready deployment. No CLI snapshots or preview alias moves as substitutes. Main publication is a separately approved fast-forward of the verified dev SHA; obtain separate approval for merging main and pushing main. Production protection/infrastructure writes require approval too. See docs/deployment.md. These instructions supplement deterministic permission rules, not replace them. String matching and classifier guidance cannot enforce arbitrary script/API semantics and are not an OS sandbox. Yolo mode explicitly bypasses ask rules; it is not a production protection mode.
